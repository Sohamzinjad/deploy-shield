# DeployShield Dataset & ML Evaluation Methodology

## 1. Dataset Generation

The training dataset is fully **synthetically generated** by [`ml-service/data/gen_dataset.py`](../ml-service/data/gen_dataset.py).

```bash
python ml-service/data/gen_dataset.py --rows 50000 --seed 42
# Output: ml-service/data/dataset.csv
```

### Why synthetic generation?

- Full control over class balance (no 91:1 skew).
- Ensures attack payloads appear in **all** injection points: URL query params, POST body, and HTTP headers — not just one fixed path.
- Allows deliberate inclusion of **hard-negative samples** (see §3).
- Reproducible via `--seed`.

### Request shape matches runtime

Training rows are generated in exactly the same payload shape that the gateway emits to `ml-service`:
- `method`: one of GET / POST / PUT / DELETE.
- `url`: full path + query string (multi-segment, e.g. `/products/1234/reviews?sort=price&page=2`).
- `headers`: JSON dict with `user-agent`, `content-type`, `accept`, etc.
- `body`: JSON string for POST/PUT, empty string for GET/DELETE.

This closes the train/serve feature skew identified in the original audit.

## 2. Class Balance

| Label | Target rows | % of dataset |
|-------|------------|-------------|
| benign | ~42,500 | ~70% |
| sqli | ~2,500 | ~17% |
| xss | ~2,500 | ~17% |
| cmdi | ~2,500 | ~17% |

**Overall ratio: ~70% benign / 30% attack** across three balanced attack classes.

This is a deliberate departure from the original dataset (91% benign, 0.3% cmdi). It removes the trivial majority-class baseline advantage while giving the model enough attack signal for each class.

The `RandomForestClassifier` is trained with `class_weight='balanced'` as an additional safeguard.

---

## 3. Hard-Negative Strategy

A key reason the original model had poor precision on real traffic was the absence of benign requests that look "suspicious" in isolation. Approximately **17% of benign training rows** are *hard negatives* — they contain apostrophes, angle brackets, SQL-like words, or bash-like tokens in a natural context:

| Hard-negative example | Why it looks dangerous | Why it is benign |
|---|---|---|
| `/search?q=O'Brien's+cafe` | Contains `'` (SQL quote) | A real search query |
| `/docs/select-the-best-laptop` | Contains `select` | A blog post slug |
| `/products?q=cat+food` | Contains `cat` | A product search |
| `User-Agent: curl/8.4.0` | Contains `curl` | A legitimate API client |
| `/search?q=alert+me+when+in+stock` | Contains `alert` | Notification preference |

Without these, the model learns "contains apostrophe → attack" which kills precision.

## 4. Evaluation Metrics

Do **not** report only overall accuracy on an imbalanced dataset. Use:

- **Per-class F1 score** (`classification_report` in `train.py`).
- **Confusion matrix** to identify which attack types are missed vs. mis-classified.
- **Majority-class baseline** for comparison (printed by `train.py`).
- **Threshold calibration curve**: detection rate vs. FPR across thresholds (generated by `ml-service/threshold_sweep.py`, saved to `docs/threshold_curve.png`).
- **Independent evaluation** on traffic captured from sqlmap/ZAP via `evaluation/evaluate.py`.

---

## 5. Independent Evaluation Set

To demonstrate generalisation beyond training data, a held-out evaluation set is captured by running real attack tools **through the gateway** against the sample app:

```bash
# With docker compose up, sample app deployed:
python evaluation/collect_traffic.py --target http://localhost:8000/apps/<APP_ID>
python evaluation/evaluate.py --dataset evaluation/eval_dataset.csv
```

This traffic was **never used in training**. It is the primary evidence that the system generalises to real attack patterns rather than just fitting the training distribution.
